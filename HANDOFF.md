## 1. Mission

Build a full-stack **Task Manager** for a senior Python/Django interview
(Ballastlane). A technical panel will review the repo, watch a demo, and ask
the candidate to explain **every** coding decision. So:

- Prefer code the candidate can explain in one sentence.
- No unexplained dependencies, no clever tricks, no dead code.
- Every non-obvious choice gets a short ADR in `docs/adr/`.

### Grading criteria (from the brief)

1. **Clean Architecture**: separation of concerns, independent components.
2. **Testing**: at least 80% coverage (target 90%+). TDD preferred.
3. **Code quality**: organized, readable, best practices.
4. **Functionality**: works with no errors; **no browser console warnings**.
5. **Presentation**: demo + architecture explanation.
6. **GenAI fluency**: prompt, output sample, validation, corrections.

### Required features (from the brief)

- CRUD tasks; assign tasks to users; mark complete; filter by status and due date.
- JWT auth, pagination, PostgreSQL (SQLite allowed for tests only).
- Unit tests, 80%+ coverage.
- Dockerfile + docker-compose (app + DB).
- README, API docs, pyproject + uv, pre-commit.
- Rate limiting. Background processing (Celery + Redis).
- Frontend (React) with CRUD, responsive, structured. Seeded demo data and credentials.

### Target role signals (job post)

Python 3.12+, Django 6.x, PostgreSQL performance, Docker (AWS ECS-style
images), pytest, clean architecture, HTMX/Alpine (plus), React.

## 3. Architecture

Feature-oriented, four layers per feature (`tasks`, `users`).

```
backend/
  config/                  settings (base/local/prod/test), urls, celery.py, wsgi/asgi
  apps/
    tasks/
      domain/              pure Python: entities, value objects, rules, domain errors
      application/         use cases + ports (typing.Protocol): TaskRepository, Notifier, Clock
      infrastructure/      Django ORM models, repository impl, Celery notifier, migrations
      interfaces/          DRF views, serializers, filters, permissions, URL conf, DI wiring
      tests/
    users/                 same layout
  manage.py
frontend/
  src/
    api/                   generated/ (never edit) + thin wrapper, session, error mapping
    features/auth/  features/tasks/
    components/            shared, small UI pieces
    routes/
docs/
  adr/                     one file per decision, short
  GENAI.md                 prompt, output sample, validation, mistakes log
  architecture.md          C4-style diagram (mermaid) + request walkthrough
openapi.yaml               committed, regenerated by CI check
PLAN.md                    phases, status, deviations
```

### Dependency rules (enforced by import-linter)

- `domain` imports **nothing** from Django, DRF, Celery, or other layers.
- `application` imports only `domain` (and the standard library). No Django.
- `infrastructure` imports `application` and `domain`. It implements the ports.
- `interfaces` imports `application` and `domain`. It must not touch the ORM
  directly. It calls use cases.
- Composition root (dependency wiring) lives in `interfaces/` only.
- Cross-feature imports go through the other feature's `application` API only.

Write the import-linter contracts in Phase 0 and keep CI red if they break.

### Pragmatism clause

If a rule forces absurd code (for example, pagination and filtering of
querysets), the repository may return a queryset-backed page object. Record
it in an ADR. Do not silently bend the rules.

## 4. Domain and functional decisions

**Entities**

- `User`: id, email (unique, login identifier), name, is_active. Django custom
  user model with email login, created in the first migration.
- `Task`: id, title (1–200 chars, trimmed, not blank), description (optional),
  status, due_date (date, optional), created_by, assignee (optional),
  completed_at (optional), created_at, updated_at.
- `TaskStatus`: `todo`, `in_progress`, `done`. Stored as a string with a
  check constraint (not a DB enum).

**Rules**

- Any authenticated user can **read/list** all tasks.
- The **creator** can update any field, reassign, and delete.
- The **assignee** can change `status` (including completing) and nothing else.
- Everyone else: read only. Violations return 403.
- Setting `status=done` sets `completed_at` once. Moving away from `done`
  clears it. Sending `done` again keeps the first `completed_at`.
- Assignee must be an active existing user. Unknown assignee returns 400
  with a field error (validation), not 409.
- `due_date` may be in the past on update; on **create** it must not be
  before today (decide and record in an ADR).
- Overdue = `due_date < today` and `status != done`. Computed via the `Clock`
  port, never `date.today()` inside domain code.

**List endpoint**

- Filters: `status`, `due_before`, `due_after` (inclusive), `assignee`
  (id, or `me`), `overdue` (bool).
- Order: `due_date` ascending, NULLs last, then `id` (stable pagination).
- Page-number pagination: `page`, `page_size` (default 10, max 100).
- Indexes: `(status, due_date)`, `assignee_id`, `created_by_id`. Add a partial
  index only if `EXPLAIN` shows a benefit; save the `EXPLAIN` output in `docs/`.

**Errors**: one error shape for everything, including 401, 403, 404, 429 and
validation errors. Define it once and document it in OpenAPI.

## 5. API surface (prefix `/api/v1`)

| Method / path | Purpose |
| --- | --- |
| `POST /auth/login` | email + password returns access token and user; refresh set as HttpOnly cookie |
| `POST /auth/refresh` | rotate refresh, return a new access token |
| `POST /auth/logout` | blacklist the refresh token, clear the cookie |
| `GET /users` | list active users (for the assignee picker) |
| `GET /users/me` | current user |
| `GET /tasks` | list with filters and pagination |
| `POST /tasks` | create |
| `GET /tasks/{id}` | detail |
| `PATCH /tasks/{id}` | partial update (status, assignee, etc.) |
| `DELETE /tasks/{id}` | delete |
| `POST /tasks/{id}/complete` | optional convenience; if added, it must call the same use case as PATCH |
| `GET /health` | liveness and readiness (DB, Redis) |
| `GET /schema`, `/docs`, `/redoc` | OpenAPI + Swagger UI + ReDoc |

Throttles: anonymous 20/min, authenticated 100/min, login 5/min per IP.
Return `Retry-After` on 429.

## 6. Background tasks

1. **Assignment notification.** When a task is assigned or reassigned, send a
   notification (email to Mailpit in Docker, plus a log line).
   - Enqueue with `transaction.on_commit`, so a rollback never sends it.
   - Task payload is IDs only; the worker re-reads current state.
   - Idempotent. Retries with backoff.
   - **If Redis is down, the request must still succeed** (log and degrade).
     Test this explicitly. Do not let the request hang.
2. **Overdue digest (Celery beat).** Daily job that finds overdue tasks and
   notifies assignees. Make the schedule configurable.

The use case depends on the `Notifier` port, never on Celery.

## 7. OpenAPI as the contract

- `drf-spectacular`: every view has an explicit `@extend_schema` (request,
  responses, errors 400/401/403/404/429, parameters).
- `ENUM_NAME_OVERRIDES` so `TaskStatus` is one named enum.
- Declare the JWT bearer security scheme and the pagination envelope.
- Generate with `manage.py spectacular --file openapi.yaml --validate`. Commit it.
- Frontend: `openapi-typescript` writes `src/api/generated/schema.d.ts`
  (header: do not edit). Components never import generated code directly;
  they go through `src/api/`.
- CI: (1) regenerate the schema and `git diff --exit-code`, (2) regenerate TS
  types and run `tsc`, (3) optional: Schemathesis against the running API.
- If a generated type is wrong, fix the serializer annotation. Do not
  patch the output.

## 8. Testing and TDD

- **Write the failing test first**, run it, see it fail, then write the code.
  Commit red then green when practical (`test:` then `feat:`).
- Levels:
  - Domain: plain pytest, no DB, no Django.
  - Application: use cases with in-memory fakes of the ports.
  - Infrastructure: repository tests against real Postgres.
  - Interface/API: status codes, permissions, validation, pagination,
    filters, throttling, response shape.
- Required cases: expired / tampered / blacklisted tokens, 401 vs 403,
  each permission rule, blank/whitespace title, unknown assignee, past
  `due_date`, page past the end, `page_size` 0 and 101, empty results,
  idempotent completion, Redis down, no N+1 on the list (`django_assert_num_queries`).
- Coverage gate: `--cov-fail-under=90` on the backend. Frontend: component and
  hook tests for auth, list, filters, form, delete.
- Do not mock what you own. Use fakes for ports, real DB for infrastructure.
- Tests must be deterministic: inject the clock, no sleeps, no network.

## 9. Frontend requirements

- Routes: `/login`, `/tasks` (list), task create/edit form (page or accessible dialog).
- **Filters and page live in the URL query string** (reload and share work).
- Server state in TanStack Query; local UI state in `useState`. No global
  state library.
- Auth: access token **in memory**; refresh via HttpOnly cookie; on 401 try
  one refresh, otherwise go to login. Put this in one module.
- Must have: loading, empty, and error states; optimistic or invalidated
  update on complete; delete confirmation; disabled actions the user may not
  perform (the API still enforces them); overdue badge.
- Responsive from 320px, semantic HTML, labels, keyboard navigable, focus
  management on dialogs.
- **Zero console warnings or errors.** Verify in a real browser run.
- Minimal CSS approach, one styling method, no UI kit unless justified in an ADR.
- Format dates in one helper.

## 11. Working agreement (how you operate)

Work in **phases**. After each phase: stop, report, wait for "go".

| Phase | Output |
| --- | --- |
| 0 | Repo skeleton, uv, pyproject, pre-commit, import-linter contracts, CI skeleton, compose with db/redis, `PLAN.md`, initial ADRs. Nothing runs yet beyond a health check. |
| 1 | Domain + application layer, fully test-driven, no Django. |
| 2 | Infrastructure (models, migrations, repo) + integration tests. |
| 3 | Interfaces: auth, tasks API, throttling, OpenAPI annotations, `openapi.yaml`. |
| 4 | Celery: notification, beat job, Redis-down behavior. |
| 5 | Frontend: generated types, auth, list/filters/URL state, forms, tests. |
| 6 | Docker polish, seed command, CI complete, README, `docs/architecture.md`. |
| 7 | Hardening: `EXPLAIN` evidence, security review, console check, clean-clone run. |

Each phase report must contain: what changed, commands you ran and their
results, deviations from this file, open questions.

**Rules**

- Keep `PLAN.md` current (status + deviations).
- Never claim a check passed unless you ran it. Paste the real output summary.
- Do not add features, dependencies, or abstractions that are not in this file
  without asking.
- Small commits, Conventional Commits (`feat:`, `test:`, `fix:`, `docs:`, `chore:`).
- If you find a gap or contradiction in this file, list it and ask. Do not
  silently decide.

## 12. Writing style

only where behavior is not obvious.
